# Security policy

## Supported versions

| Version | Supported |
| --- | --- |
| 0.1.x | Yes — this is the only line |

## Reporting a vulnerability

Please **do not open a public issue** for a security problem.

Use GitHub's private vulnerability reporting on this repository
(`Security → Report a vulnerability`), which creates a private advisory thread
with the maintainers.

Please include:

* what you observed and where (server route, protocol message, client screen);
* the smallest set of steps that reproduces it;
* the impact as you see it (for example "a paired device can execute an action
  outside the allowlist");
* whether it needs a paired device, an owner token, or neither.

What to expect:

* an acknowledgement within a few days;
* an assessment and, if confirmed, a fix or a documented mitigation;
* credit in the release notes unless you prefer to stay anonymous.

## Please do not

* run automated scanners against someone else's deployment of this project;
* test against a device you do not own;
* include real credentials, device tokens or personal data in a report.

## Scope

| In scope | Out of scope |
| --- | --- |
| The server (`server/src`) | A vulnerability in Android itself |
| The device protocol (`docs/PROTOCOL.md`) | A vulnerability in your hosting provider |
| The Android client (`android/`) | Vulnerabilities requiring a rooted device |
| The bot (`server/src/bot`) | Missing certificate pinning (documented limitation) |
| Credential handling and logging | Reports generated by an automated scanner with no reproduction |

## Known limitations

These are documented, accepted design decisions — reporting them again will not
change the assessment, but a *new* way to exploit one will:

1. The device token is stored in app-private `SharedPreferences` on the phone
   (Android app sandbox, not hardware-backed). See
   [docs/SECURITY_MODEL.md](docs/SECURITY_MODEL.md).
2. No TLS certificate pinning; validation uses the system trust store.
3. An accessibility service is powerful by design. It is bound, not exported, and
   only acts on an instruction you sent.
4. The AI model is not a security boundary: it proposes, the policy engine and
   the phone decide.

## If your device or token is compromised

1. Revoke the device server-side:
   `POST /api/v1/devices/:deviceId/revoke` with your owner token, or `/revoke <id>`
   in the bot. The connected phone wipes its local copy immediately.
2. Rotate the owner token (`OWNER_API_TOKENS`) and the AI key if either could have
   been exposed.
3. Review recent task history: `GET /api/v1/tasks`.
4. Re-pair the phone only after you understand how it happened.
